OCTO INDUSTRIES — UNIVERSAL GAME ACQUISITION, EXTRACTION, PRESERVATION, SELF-HOSTING, AUTOMATIC SAVING, PLAYABILITY AND HUB INTEGRATION SYSTEM
1. PRIMARY MISSION
Acquire the ACTUAL target game.
The objective is to:
	•	Find the original game.
	•	Acquire its actual playable files.
	•	Verify the acquired artifact.
	•	Extract available resources.
	•	Preserve original gameplay.
	•	Localize game files.
	•	Store the game inside the Octo Industries repository.
	•	Self-host the game wherever technically and legitimately possible.
	•	Implement automatic progress saving.
	•	Integrate the game throughout Octo Industries.
	•	Verify that the game is genuinely playable.
The required architecture is:
ACTUAL GAME ↓ VERIFIED GAME ARTIFACT ↓ EXTRACTED GAME FILES ↓ OCTO INDUSTRIES REPOSITORY ↓ LOCALIZED GAME RUNTIME ↓ AUTOMATIC SAVE SYSTEM ↓ OCTO INDUSTRIES HUB ↓ PLAYABLE GAME
Do not mistake a game listing, external link, screenshot, iframe, launcher, or promotional webpage for an acquired game.
2. AUTHORIZATION AND TECHNICAL SCOPE
Assume the project has obtained the permissions necessary for its intended acquisition, preservation, modification, hosting, and integration.
Focus on technical implementation.
Respect applicable platform restrictions, access controls, privacy requirements, and security boundaries.
Do not bypass DRM, authentication, payment requirements, or other technical access restrictions.
If an artifact cannot legitimately be obtained, investigate alternative legitimate sources and document the limitation.

10.1 NON-SUBSTITUTION AND STOP RULE
Never create, code, generate, or register a reconstruction, clone, imitation, remake, or substitute game when the requested original game cannot be obtained.
This prohibition applies even when:
	•	The requester says they own the rights or gives permission.
	•	The original download or game host returns an error or blocks access.
	•	Gameplay descriptions, screenshots, videos, or other references are available.
	•	An original game artifact appears unavailable.
Only create a reconstruction or substitute when the user explicitly asks for one as a separate, distinct task.
When the original cannot be legitimately acquired:
	1.	Stop acquisition and implementation work for that game.
	2.	Do not add a placeholder, external link, iframe, wrapper, clone, or reconstruction to the collection.
	3.	Do not change the game registry or create a game folder for it.
	4.	Report sources checked, evidence, exact errors or limitations, and the next legitimate step needed to proceed.
	5.	Keep the task classified as blocked or unavailable; do not claim the requested game is done.
Do not bypass access controls, authentication, payment restrictions, anti-bot controls, or HTTP access denials to obtain a game. A rights or permission statement does not itself grant technical access to a third-party host.
11. AUTHENTICITY AND NON-SUBSTITUTION
The objective is only the actual requested game, not a clone, imitation, remake, or substitute.
Preserve the authentic game and its behavior when the original artifact is legitimately acquired.
References such as descriptions, screenshots, gameplay footage, audio, animations, or metadata may support verification and preservation of an acquired original; they do not authorize or justify creating a replacement game.
Never reconstruct or imitate a game as an acquisition fallback. Follow section 10.1 and stop with a factual report unless the user separately and explicitly requests a reconstruction.

13. UNIVERSAL AUTOMATIC GAME SAVE SYSTEM
Primary objective
Implement a centralized game persistence architecture for ALL imported Octo Industries games.
Every game containing progression, levels, checkpoints, achievements, statistics, unlocks, settings, or other persistent information must preserve its supported progress automatically.
Expected experience:
Player opens Octo Industries. ↓ Player opens a game. ↓ Player completes levels or reaches checkpoints. ↓ Progress is automatically saved. ↓ Player closes the website. ↓ Player returns later. ↓ Player opens the same game. ↓ The latest valid save is detected. ↓ Continue becomes available. ↓ Player resumes previous progress.
The player should not need to manually save progress.
13.1 Save timing
Save automatically at:
	•	Checkpoints.
	•	Completed levels.
	•	Completed stages.
	•	Important progression milestones.
	•	Game exit when a reliable save opportunity exists.
Do not continuously save every movement or action.
Use original game save events wherever available.
Do not rely exclusively on browser-close events because browsers and mobile operating systems can terminate pages without executing shutdown handlers.
Prioritize reliable checkpoint and level-completion saves.
13.2 Data to preserve
Preserve all relevant supported data:
	•	Current level.
	•	Completed levels.
	•	Current stage.
	•	Checkpoints.
	•	Campaign progress.
	•	Unlocked levels.
	•	Characters.
	•	Abilities.
	•	Inventory.
	•	Currency.
	•	Scores.
	•	High scores.
	•	Achievements.
	•	Quests.
	•	Player statistics.
	•	Game settings.
	•	Control preferences.
	•	Customization.
	•	Other game-specific progression.
Preserve actual supported game state, not merely screenshots or metadata.
13.3 Automatic Continue
When a game is reopened:
	1.	Identify its save.
	2.	Validate the save.
	3.	Load the latest valid progress.
	4.	Restore the supported game state.
	5.	Make Continue available.
Never unnecessarily restart a player from Level 1 when valid progress exists.
Where the original game has a Continue option, preserve its original behavior.
Do not force automatic mid-level restoration if the game only supports checkpoint-based restoration.
13.4 Device-wide persistence
All games must retain their own independent saves on the device and browser profile being used.
Example:
Game A:
	•	Level 5 completed.
Game B:
	•	World 2 unlocked.
Game C:
	•	High score preserved.
Game D:
	•	Campaign halfway completed.
Closing Octo Industries must not erase these saves.
When reopening the same website on the same browser and device, restore each game's own progress.
13.5 Storage architecture
Preferred storage:
	1.	IndexedDB for structured and larger game saves.
	2.	LocalStorage for lightweight settings and metadata.
	3.	Existing project storage systems where appropriate.
Never rely exclusively on:
	•	In-memory variables.
	•	SessionStorage.
	•	Temporary runtime state.
Separate saves using:
	•	Game ID.
	•	Save slot.
	•	Browser/device profile.
	•	Save version.
Use one centralized save-management interface.
Request persistent browser storage where supported, and account for browser quotas and eviction policies.
Do not promise survival after users clear browser data or storage is removed by the browser or operating system.
13.6 Original game save compatibility
Inspect original save systems before implementing new ones.
Support appropriate adapters for:
	•	Unity WebGL.
	•	HTML5.
	•	Phaser.
	•	Construct.
	•	Godot.
	•	GameMaker.
	•	Other compatible engines.
Preserve original save mechanisms whenever possible.
Avoid competing save systems that corrupt original progress.
If an original runtime does not expose sufficient game-state information, do not pretend exact-state restoration is possible.
Implement the most reliable supported checkpoint or progression-based persistence.
13.7 Save slots
Every game must have independent save data and support its appropriate save-slot structure.
Do not overwrite another game's saves.
Where multiple save slots are supported, keep them independently identifiable.
13.8 Save integrity

13.11 Cloud synchronization
Device-local saving is the primary requirement.
Cloud synchronization is optional.
If an existing authenticated backend is available and authorized:
	•	Synchronize local saves when possible.
	•	Preserve offline functionality.
	•	Avoid overwriting newer saves.
	•	Detect conflicts.
	•	Provide safe recovery.
	•	Keep cloud and local versions distinguishable.
Do not make cloud synchronization mandatory for locally playable games.
Do not assume saves transfer to another device without an actual synchronization mechanism.
13.12 Save levels
Classify each game:
SAVE LEVEL 1 — FULL STATE PERSISTENCE
Full supported gameplay state restored.
SAVE LEVEL 2 — CHECKPOINT PERSISTENCE
Latest supported checkpoint restored.
SAVE LEVEL 3 — PROGRESSION PERSISTENCE
Completed levels, unlocks, and progression preserved.
SAVE LEVEL 4 — LIMITED PERSISTENCE
Only supported settings or statistics preserved.
SAVE LEVEL 5 — NO RELIABLE PERSISTENCE
No reliable save mechanism available.
Never falsely claim a higher save level.

	9.	Verify Continue.
	10.	Verify previous progress.
	11.	Test a second game.
	12.	Confirm the two games have independent saves.
Test browser restarts where feasible.
